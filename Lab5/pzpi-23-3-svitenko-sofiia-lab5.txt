2 ЗАВДАННЯ

     Підготувати та представити коротку презентацію цілісного проекту, реалізованого в ході двох семестрів навчання. Презентація має включати демонстраційне відео тривалістю 4–6 хвилин із оглядом основних функцій системи, опис того, що зі запланованого вдалося реалізувати, а що залишилось поза межами виконання. Звіт повинен містити: короткий опис проекту, перелік запланованих та виконаних функцій, матеріали презентації та посилання на відеодемо.


3 ОПИС ВИКОНАНОЇ РОБОТИ

     PrintMaster — програмна система управління 3D-друком, що автоматизує повний цикл обробки замовлення: від завантаження STL-файлу до фізичного виконання друку. Система складається з чотирьох компонентів: IoT-модуля на базі ESP32 (MicroPython), серверної частини на ASP.NET Core 10 з PostgreSQL та EF Core, веб-застосунку на React Router 7 з TypeScript та мобільного Android- застосунку на Kotlin. Усі компоненти взаємодіють через єдиний REST API з JWT-автентифікацією. Серверна частина є центральним вузлом: вона приймає STL- файли, запускає PrusaSlicer для генерації G-code, розраховує вартість друку, керує принтерами та надає API для клієнтських застосунків і IoT-пристрою.

3.1 Мобільний застосунок Android

     У лабораторній роботі №2 розроблено нативний Android-застосунок PrintMaster мовою Kotlin з Jetpack Compose. Архітектура побудована за чотиришаровим принципом: шар UI (Jetpack Compose екрани), шар ViewModel (StateFlow), шар Repository та шар даних (Ktor + SharedPreferences). Мережева взаємодія реалізована через Ktor з плагіном Auth Bearer: токен зберігається у SharedPreferences та автоматично додається до кожного запиту. Реалізовано офлайн-кеш на SharedPreferences з fallback-поведінкою — застосунок відображає кешовані завдання при відсутності мережі. Застосунок підтримує чотири екрани: LoginScreen, JobListScreen зі StatusChip (Pending / Printing / Completed / Failed), NewJobScreen із вибором STL-файлу через системний picker та dropdowns матеріалу і принтера, PrinterMapScreen із Google Maps Compose та маркерами принтерів. Локалізацію реалізовано для двох мов: англійської та української.
3.2 Веб-застосунок

     У лабораторній роботі №3 розроблено SPA PrintMaster Web на React Router 7 з TypeScript та Tailwind CSS v4. Маршрутизація побудована на файловій системі: layout-файли «_user.tsx» та «_admin.tsx» реалізують «clientLoader» з перевіркою ролі та автоматичним редиректом. Мережева взаємодія централізована в «lib/ api.ts» через axios з двома interceptor-ами: request interceptor додає JWT-токен, response interceptor обробляє 401 з автоматичним logout. Локалізація реалізована через i18next з «LanguageDetector». Реалізовано 9 сторінок: LoginPage, JobsPage зі StatusChip, NewJobPage з drag-and-drop завантаженням STL (Drag Events API), адмін-сторінки DashboardPage (Recharts: PieChart + BarChart), PrintersPage (inline CRUD), MaterialsPage (CRUD + color picker), UsersPage (зміна ролей), LogsPage та ExportImportPage з JSON-резервним копіюванням.
3.3 Серверна частина та масштабування

     У лабораторній роботі №4 реалізовано горизонтальне масштабування серверної частини PrintMaster через Kubernetes. Реалізовано клас «DbHealthCheck», що виконує «SELECT 1» через EF Core і реєструється як readiness та liveness probe

— Kubernetes маршрутизує трафік до pod-а лише після успішної відповіді. Описано повну k8s-інфраструктуру: namespace «printing-system», StatefulSet PostgreSQL із PVC, Deployment серверної частини з двома репліками та стратегією RollingUpdate (maxUnavailable: 0), NodePort-сервіс та HorizontalPodAutoscaler із масштабуванням від 1 до 6 реплік за CPU > 70% та Memory > 80%. Навантажувальне тестування Locust показало, що перехід від 1 репліки до 2 знижує середній час відповіді з 267 до 25 мс (у 10 разів) при збереженні нульового відсотка помилок.

ВИСНОВКИ

     В результаті виконання лабораторної роботи підготовлено презентацію завершеного проекту PrintMaster, що охоплює всі компоненти системи, реалізовані в ході двох семестрів навчання. Система складається з чотирьох компонентів: IoT-модуля ESP32 (курс ATRK), серверної частини ASP.NET Core 10 з Kubernetes- масштабуванням, веб-застосунку React Router 7 та Android-застосунку Kotlin.
     Із запланованих функцій реалізовано 14 із 17. G-code парсинг у серверній частині  не  реалізовано  —  функціонал  присутній  в  IoT-модулі  на  Python і не потребував дублювання у бекенді. ReadWriteMany PVC використовує ReadWriteOnce у локальному minikube-кластері, що є прийнятним для навчального розгортання; перехід на NFS або MinIO заплановано в наступних релізах. ШІ- модуль автоматичного підбору параметрів друку залишено в плані наступних релізів: система вже накопичує необхідні дані (типи матеріалів, час друку, успішність), проте розробка власних моделей машинного навчання виходить за межі поточного курсу.
     Побудовано UML-діаграму розгортання всіх компонентів системи. Підготовлено Marp-презентацію з 15 слайдів та записано відеодемо основних функцій системи.

В.1.1 Запит 1: Підготовка elevator pitch для системи управління 3D-друком

     Внесок автора: Формулювання запиту на основі власного розуміння цільової аудиторії, самостійний вибір формату (проблема → рішення → переваги), редагування відповіді під стиль презентації.

Адміністратор бачить завантаженість принтерів, споживання матеріалів та вартість кожного замовлення в реальному часі. Pitch:
«PrintMaster перетворює вашу 3D-лабораторію з ручного цеху на автоматизований конвеєр — від завантаження файлу до готової деталі без єдиного термінального вікна.»
Уточнення:
«Як стисло описати технічний стек у двох рядках для технічного слайду?» Відповідь: «ASP.NET Core 10 · PostgreSQL · EF Core · JWT — серверна частина.

     В.1.2 Запит 2: Структура UML-діаграми розгортання для системи з IoT та Kubernetes
Назва інструменту та версія: Claude Sonnet 4.6
     Мета використання: Визначити правильний рівень деталізації та нотацію для UML deployment diagram, що охоплює чотири компоненти: ESP32, мобільний Android, React SPA та ASP.NET Core + Kubernetes.
     Внесок автора: Формулювання запиту з урахуванням реальної топології, самостійний вибір інструменту (PlantUML), розміщення компонентів по вузлах, адаптація відповіді під наявні k8s маніфести.
Початковий запит:
     «Яку нотацію використати для UML deployment diagram системи де є: ESP32, Android-смартфон, браузер з SPA, і сервер у Kubernetes з двома репліками API та StatefulSet PostgreSQL? Покажи структуру PlantUML.»
     Відповідь: У UML deployment diagram вузлами («node») є фізичні або віртуальні середовища виконання. ESP32, смартфон та браузер — окремі «node». Kubernetes-кластер — «node» з вкладеними артефактами: дві репліки «api-3d» та
«postgres-0». Зв’язки між вузлами — «communication path» з протоколом (HTTP/ REST, UART). PlantUML: «node "ESP32"» → «node "Kubernetes"» з «component "api-3d [×2]"» та «component "postgres-0"».
Уточнення:
«Як відобразити HorizontalPodAutoscaler на deployment diagram?»
     Відповідь: HPA є k8s-об’єктом керування, а не вузлом виконання — на deployment diagram його показують як «note» або окремий «component "HPA\nmin:1 max:6"» всередині Kubernetes-вузла зі стрілкою «controls» до Deployment.
     В.1.3 Запит 3: Аналіз результатів навантажувального тестування для презентації
Назва інструменту та версія: Claude Sonnet 4.6
     Мета використання: Сформулювати висновки з результатів Locust-тестування (1/2/4 репліки) у форматі, придатному для слайду та усної доповіді.

     Внесок автора: Надання фактичних CSV-результатів, самостійний аналіз причини відсутності приросту між 2 і 4 репліками (PostgreSQL bottleneck), редагування відповіді для включення у звіт та презентацію.
Початковий запит:
     «Допоможи сформулювати висновки з навантажувального тестування. 1 репліка — 26.7 RPS, avg 267 мс, p95 1800 мс. 2 репліки — 30.7 RPS, avg 25 мс, p95
120 мс. 4 репліки — 30.3 RPS, avg 27 мс, p95 200 мс. Помилок 0%.»
     Відповідь: Ключовий висновок: перехід 1→2 репліки дав 10-кратне зниження середнього часу відповіді — усунуто CPU-bottleneck на bcrypt-хешуванні при логіні. Відсутність приросту 2→4: вузьке місце змістилось на PostgreSQL (єдиний StatefulSet). Для слайду: «1→2 репліки: avg −90%, p95 −93%. 2→4 репліки: плато
— bottleneck PostgreSQL та port-forward тунель ( 30 req/s).»
