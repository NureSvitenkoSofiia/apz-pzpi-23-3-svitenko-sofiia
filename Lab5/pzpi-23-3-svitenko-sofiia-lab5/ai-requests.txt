== Запити до штучного інтелекту

=== Запит 1: Підготовка elevator pitch для системи управління 3D-друком

Назва інструменту та версія: Claude Sonnet 4.6

Мета використання: Сформулювати стислий опис системи PrintMaster у форматі elevator pitch для слайду-презентації з акцентом на цінність для кінцевого користувача, а не на технічну реалізацію.

Внесок автора: Формулювання запиту на основі власного розуміння цільової аудиторії, самостійний вибір формату (проблема → рішення → переваги), редагування відповіді під стиль презентації.

Початковий запит:

«Допоможи сформулювати elevator pitch для системи управління 3D-друком PrintMaster. Система приймає STL-файли, автоматично нарізає їх PrusaSlicer, передає G-code на ESP32 через API, відстежує прогрес та показує аналітику адміністратору. Є веб і мобільний клієнти. Аудиторія — технічна, але потрібен акцент на бізнес-цінності.»

Відповідь: PrintMaster усуває ручний етап підготовки файлів до 3D-друку: замість локального запуску слайсера та ручного перенесення файлів оператор завантажує STL через браузер або смартфон — система сама конвертує, ставить у чергу та звітує про результат. Адміністратор бачить завантаженість принтерів, споживання матеріалів та вартість кожного замовлення в реальному часі. Pitch: «PrintMaster перетворює вашу 3D-лабораторію з ручного цеху на автоматизований конвеєр — від завантаження файлу до готової деталі без єдиного термінального вікна.»

Уточнення:

«Як стисло описати технічний стек у двох рядках для технічного слайду?»

Відповідь: «ASP.NET Core 10 · PostgreSQL · EF Core · JWT — серверна частина. React Router 7 · Kotlin · MicroPython · Kubernetes — клієнти та інфраструктура.»

=== Запит 2: Структура UML-діаграми розгортання для системи з IoT та Kubernetes

Назва інструменту та версія: Claude Sonnet 4.6

Мета використання: Визначити правильний рівень деталізації та нотацію для UML deployment diagram, що охоплює чотири компоненти: ESP32, мобільний Android, React SPA та ASP.NET Core + Kubernetes.

Внесок автора: Формулювання запиту з урахуванням реальної топології, самостійний вибір інструменту (PlantUML), розміщення компонентів по вузлах, адаптація відповіді під наявні k8s маніфести.

Початковий запит:

«Яку нотацію використати для UML deployment diagram системи де є: ESP32, Android-смартфон, браузер з SPA, і сервер у Kubernetes з двома репліками API та StatefulSet PostgreSQL? Покажи структуру PlantUML.»

Відповідь: У UML deployment diagram вузлами (`node`) є фізичні або віртуальні середовища виконання. ESP32, смартфон та браузер — окремі `node`. Kubernetes-кластер — `node` з вкладеними артефактами: дві репліки `api-3d` та `postgres-0`. Зв'язки між вузлами — `communication path` з протоколом (HTTP/REST, UART). PlantUML: `node "ESP32"` → `node "Kubernetes"` з `component "api-3d [×2]"` та `component "postgres-0"`.

Уточнення:

«Як відобразити HorizontalPodAutoscaler на deployment diagram?»

Відповідь: HPA є k8s-об'єктом керування, а не вузлом виконання — на deployment diagram його показують як `note` або окремий `component "HPA\nmin:1 max:6"` всередині Kubernetes-вузла зі стрілкою `controls` до Deployment.

=== Запит 3: Аналіз результатів навантажувального тестування для презентації

Назва інструменту та версія: Claude Sonnet 4.6

Мета використання: Сформулювати висновки з результатів Locust-тестування (1/2/4 репліки) у форматі, придатному для слайду та усної доповіді.

Внесок автора: Надання фактичних CSV-результатів, самостійний аналіз причини відсутності приросту між 2 і 4 репліками (PostgreSQL bottleneck), редагування відповіді для включення у звіт та презентацію.

Початковий запит:

«Допоможи сформулювати висновки з навантажувального тестування. 1 репліка — 26.7 RPS, avg 267 мс, p95 1800 мс. 2 репліки — 30.7 RPS, avg 25 мс, p95 120 мс. 4 репліки — 30.3 RPS, avg 27 мс, p95 200 мс. Помилок 0%.»

Відповідь: Ключовий висновок: перехід 1→2 репліки дав 10-кратне зниження середнього часу відповіді — усунуто CPU-bottleneck на bcrypt-хешуванні при логіні. Відсутність приросту 2→4: вузьке місце змістилось на PostgreSQL (єдиний StatefulSet). Для слайду: «1→2 репліки: avg −90%, p95 −93%. 2→4 репліки: плато — bottleneck PostgreSQL та port-forward тунель (~30 req/s).»
