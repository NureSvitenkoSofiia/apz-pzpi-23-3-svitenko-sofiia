2 ЗАВДАННЯ

     Реалізувати горизонтальне масштабування серверної частини системи PrintMaster: підготувати серверну частину на ASP.NET Core 10 до stateless-роботи, реалізувати ендпоінт перевірки стану системи, розгорнути кілька ідентичних реплік серверної частини у Kubernetes-кластері з автоматичним масштабуванням за навантаженням, провести навантажувальне тестування за допомогою Locust та порівняти продуктивність системи при різній кількості активних реплік.


3 ОПИС ВИКОНАНОЇ РОБОТИ

     У ході виконання лабораторної роботи реалізовано горизонтальне масштабування серверної частини системи PrintMaster за допомогою Kubernetes (minikube / Docker Desktop k8s). Підготовлено серверну частину до stateless- розгортання, реалізовано власний health check, описано повну інфраструктуру у Kubernetes-маніфестах, реалізовано автоматичне масштабування через HorizontalPodAutoscaler та проведено навантажувальне тестування за допомогою Locust.

3.1 Стратегія масштабування

     Для системи PrintMaster обрано горизонтальне масштабування — запуск кількох ідентичних pod-ів серверної частини під управлінням Kubernetes- балансувальника. Такий підхід обґрунтований архітектурними властивостями сервера: автентифікація побудована на JWT-токенах (без серверних сесій), файли STL та G-code зберігаються у спільному PersistentVolume типу ReadWriteMany, а база даних PostgreSQL є зовнішнім та єдиним джерелом стану. Завдяки цьому будь- який pod може обробити будь-який запит незалежно від того, який pod обробляв попередній.
     Перед розгортанням у Kubernetes виконано дві зміни у серверному коді. До Serilog додано «WriteTo.Console()» — це дозволяє переглядати логи через «kubectl logs» у реальному часі, оскільки у k8s файлові логи недоступні без додаткових налаштувань. Також реалізовано клас «DbHealthCheck», який реєструється як Kubernetes readiness probe: при старті pod-а він виконує «SELECT 1» до PostgreSQL і повертає статус Healthy або Unhealthy — k8s маршрутизує трафік до pod-а лише після успішної перевірки.
3.2 Реалізація ендпоінту перевірки стану

     Клас «DbHealthCheck» реалізує інтерфейс «IHealthCheck» і виконує мінімальний запит до бази через EF Core:
public async Task<HealthCheckResult> CheckHealthAsync( HealthCheckContext context, CancellationToken cancellationToken =
default)
{
try
{
await _context.Database.ExecuteSqlRawAsync("SELECT 1",
cancellationToken);
return HealthCheckResult.Healthy("PostgreSQL connection OK");
}
catch (Exception ex)
{
return HealthCheckResult.Unhealthy("PostgreSQL unreachable",
ex);
}
}

     У «Program.cs» health check реєструється та відображається на ендпоінті «/ health»:

builder.Services.AddHealthChecks()
     .AddCheck<DbHealthCheck>("db"); app.MapHealthChecks("/health");
     Kubernetes використовує цей ендпоінт у двох пробах. «readinessProbe» перевіряє pod кожні 5 секунд після 15-секундної затримки ініціалізації — pod отримує трафік лише після успішної відповіді. «livenessProbe» перевіряє pod кожні 10 секунд після 30-секундної затримки — якщо pod перестає відповідати, Kubernetes автоматично його перезапускає.
3.3 Kubernetes-конфігурація

     Вся Kubernetes-інфраструктура описана у директорії «k8s/» та розгортається скриптом «k8s/deploy.sh». Маніфести організовані у два піддиректорії: «k8s/ postgres/» та «k8s/api/».
     Простір імен «printing-system» ізолює всі ресурси системи PrintMaster від інших застосунків у кластері:
# k8s/namespace.yaml apiVersion: v1
kind: Namespace metadata:
name: printing-system

     PostgreSQL розгорнуто як StatefulSet із одною репліком. StatefulSet обрано замість Deployment, оскільки він гарантує стабільну мережеву ідентичність pod-а та впорядкований порядок запуску і зупинки — це важливо для бази даних, яка зберігає стан. Дані PostgreSQL зберігаються у PersistentVolumeClaim, що захищає їх від перезапуску pod-а. Секрети (ім’я користувача та пароль) передаються через Secret-ресурс і не потрапляють у YAML-маніфести.
Серверна частина розгорнута як Deployment із двома репліками та стратегією
«RollingUpdate» («maxUnavailable: 0», «maxSurge: 1»). Такі параметри гарантують, що під час оновлення образу нові pod-и запускаються і перевіряються до зупинки старих — без перерви у доступності сервісу. Кожен pod монтує спільний PersistentVolumeClaim типу ReadWriteMany для директорії «/data», де зберігаються STL-файли та G-code. Конфіденційні змінні («ConnectionStrings  DataContext»,
«Jwt  Key») передаються через Secret, решта налаштувань — через ConfigMap.

     HorizontalPodAutoscaler автоматично масштабує Deployment від 1 до 6 реплік на основі двох метрик: CPU > 70% та Memory > 80% від заявлених resource requests. При падінні навантаження HPA поступово зменшує кількість реплік до мінімуму.
# k8s/api/hpa.yaml (спрощено) spec:
minReplicas: 1
maxReplicas: 6 metrics:
- type: Resource resource:
name: cpu target:
type: Utilization averageUtilization: 70
- type: Resource resource:
name: memory target:
type: Utilization averageUtilization: 80

     Service типу «NodePort» з портом 30080 надає зовнішній доступ до Deployment для локального тестування. У хмарному середовищі тип слід змінити на «LoadBalancer».
     Скрипт «k8s/deploy.sh» автоматизує типові операції: «build» (збірка Docker-образу), «up» (розгортання всіх маніфестів із очікуванням готовності),
«down» (видалення namespace із усіма ресурсами), «status» (перегляд pod-ів, HPA і сервісів) та «scale N» (ручне масштабування до N реплік).
3.4 Dockerfile серверної частини

Збірка Docker-образу виконується у два етапи:

FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build WORKDIR /src
COPY ["3DApi.csproj", "."] RUN dotnet restore
COPY . .
RUN dotnet publish -c Release -o /app/publish --no-restore
FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS runtime WORKDIR /app
COPY slic3r/ /opt/slic3r/
RUN chmod +x /opt/slic3r/Slic3r
RUN mkdir -p /data/stl /data/gcode /data/logs /data/backups COPY --from=build /app/publish .
ENV ASPNETCORE_URLS=http://+:8080

EXPOSE 8080
ENTRYPOINT ["dotnet", "3DApi.dll"]

     Перший етап («build») базується на «dotnet/sdk:10.0» і виконує відновлення залежностей та компіляцію. Копіювання «.csproj» до «COPY . .» дозволяє Docker кешувати шар відновлення пакетів незалежно від змін у вихідному коді. Другий етап («runtime») базується на полегшеному образі «dotnet/aspnet:10.0» і містить лише скомпільований артефакт та бінарник Slic3r, що значно зменшує розмір фінального образу.
3.5 Навантажувальне тестування

     Для навантажувального тестування реалізовано два класи Locust- користувачів у файлі «load-tests/locustfile.py». Клас «PrintingUser» моделює звичайного користувача: авторизується через «POST /api/auth/login» та виконує запити «GET /users/{id}/jobs» (вага 5), «GET /printjobs/materials» (вага 3) та «GET / health» (вага 1). Клас «AdminUser» моделює адміністратора: отримує системну статистику через «GET /api/admin/analytics/statistics/system» (вага 4), список принтерів і матеріалів (вага 2 кожен), показники успішності та список користувачів (вага 1 кожен).
     Скрипт «load-tests/run-tests.ps1» послідовно запускає тести для трьох конфігурацій — 1, 2 і 4 репліки. Параметри тестування: 50 одночасних користувачів, швидкість появи 5 на секунду, тривалість 60 секунд. Скрипт автоматично піднімає
«kubectl port-forward» і передає адресу «http://localhost:8080» у Locust. Після кожного тесту результати зберігаються в HTML та CSV форматах у директорії «load- tests/results/».

3.6 Аналіз вузьких місць

     При горизонтальному масштабуванні серверної частини PrintMaster головним вузьким місцем є спільна PostgreSQL-інстанція. Кожен pod підтримує пул з’єднань із базою: при 4 репліках загальна кількість з’єднань зростає до значення, що наближається до типового ліміту PostgreSQL 100. При масштабуванні понад
4 репліки необхідно розгортати PgBouncer як проміжний пул з’єднань або збільшувати «max_connections» у конфігурації PostgreSQL.
     Другим вузьким місцем є PersistentVolumeClaim типу ReadWriteMany для директорії «/data» (STL та G-code файли). У локальному кластері minikube та Docker Desktop k8s ReadWriteMany реалізується через hostPath, що не підходить для розподіленого розгортання. У продуктивному хмарному середовищі необхідно використовувати NFS або об’єктне сховище (MinIO, AWS S3) з відповідним StorageClass.
     Третім вузьким місцем є виклик PrusaSlicer (конвертація STL у G-code), який є CPU-інтенсивною операцією тривалістю 1–5 хвилин і блокує thread-pool ASP.NET Core. Для усунення цього обмеження доцільно перенести Slicer-виклики у фонову чергу (наприклад, Channel або Hangfire) з окремим worker-сервісом.

ВИСНОВКИ

     В результаті виконання лабораторної роботи реалізовано горизонтальне масштабування серверної частини системи PrintMaster засобами Kubernetes. Розроблено власний «DbHealthCheck», який виконує «SELECT 1» до PostgreSQL через EF Core і реєструється як readiness та liveness probe — це гарантує, що Kubernetes маршрутизує трафік лише до pod-ів із доступною базою даних. До Serilog додано Console sink для доступності логів через «kubectl logs».
Описано повну Kubernetes-інфраструктуру у директорії «k8s/»: namespace
«printing-system», StatefulSet PostgreSQL із PVC для збереження даних, Deployment серверної частини з двома репліками та стратегією RollingUpdate (maxUnavailable: 0) для нульового простою при оновленнях, NodePort-сервіс (порт 30080) та HorizontalPodAutoscaler із автоматичним масштабуванням від 1 до 6 реплік за CPU
> 70% та Memory > 80%. Спільний PVC типу ReadWriteMany забезпечує доступ до STL та G-code файлів з усіх реплік.
     Скрипт «k8s/deploy.sh» автоматизує операції збірки, розгортання, видалення та ручного масштабування. Навантажувальне тестування реалізовано у «load-tests/ locustfile.py» з двома класами Locust-користувачів (PrintingUser та AdminUser) і скриптом «run-tests.sh» для послідовного тестування 1, 2 і 4 реплік. Виявлено три вузькі місця системи: спільна PostgreSQL-інстанція (вирішується PgBouncer при > 4 репліках), ReadWriteMany PVC (вирішується NFS або MinIO у продуктивному середовищі) та CPU-інтенсивний Slicer-виклик (вирішується винесенням у фонову чергу).

ДОДАТОК В
                         Запити до ШІ В.1 Запити до штучного інтелекту
     В.1.1 Запит 1: Підготовка ASP.NET Core сервісу до stateless горизонтального масштабування
Назва інструменту та версія: Claude Sonnet 4.6
     Мета використання: Визначення вимог до серверного застосунку на ASP.NET Core 10 для коректної роботи у горизонтально масштабованому середовищі Kubernetes з кількома ідентичними репліками за єдиним балансувальником навантаження.
     Внесок автора: Формулювання запиту на основі аналізу архітектури PrintMaster, самостійна оцінка компонентів на наявність стану (JWT, Serilog, STL/ G-code файли, DbSeeder), прийняття рішення про ReadWriteMany PVC та guard у DbSeeder, реалізація DbHealthCheck і Console sink.
Початковий запит:
     «Які вимоги до ASP.NET Core застосунку для коректної роботи в режимі кількох ідентичних реплік за балансувальником навантаження? Які типові помилки призводять до некоректної роботи при горизонтальному масштабуванні?»
     Відповідь: Основна вимога — відсутність стану між запитами (stateless). Типові проблеми: збереження стану у пам’яті (in-memory кеш, статичні колекції), серверні сесії, запис у локальну файлову систему без розподіленого сховища та виконання ініціалізаційних операцій (seeding) при кожному старті без перевірки. JWT-автентифікація є stateless за визначенням і не потребує змін. Файлове сховище слід виносити у спільний том (NFS, PVC ReadWriteMany) або об’єктне сховище. Seeder повинен містити guard-умову, яка перевіряє наявність даних перед вставкою.
Уточнення:
     «Що потрібно додати до ASP.NET Core застосунку спеціально для Kubernetes, щоб кластер міг керувати lifecycle pod-а?»
     Відповідь: Необхідно реалізувати ендпоінт readiness probe — Kubernetes не надсилатиме трафік на pod до отримання успішної відповіді. Для ASP.NET Core це робиться через «IHealthCheck» та «MapHealthChecks». Liveness probe (той самий

або окремий ендпоінт) дає Kubernetes сигнал перезапустити pod, якщо він перестав відповідати. Логи слід писати у stdout/stderr («WriteTo.Console()»), оскільки файлові логи недоступні через «kubectl logs» без додаткових налаштувань.
     В.1.2 Запит 2: Конфігурація HorizontalPodAutoscaler у Kubernetes для .NET застосунку
Назва інструменту та версія: Claude Sonnet 4.6
     Мета використання: Визначення параметрів HPA для ASP.NET Core 10 API з урахуванням характеру навантаження PrintMaster (суміш легких GET-запитів і важких Slicer CPU-викликів) та обмежень локального кластера minikube / Docker Desktop.
     Внесок автора: Формулювання запиту з урахуванням специфіки проєкту (Slicer-виклики як CPU spike, resource requests 250m CPU), самостійний вибір порогів CPU 70% і Memory 80%, встановлення maxReplicas 6 з урахуванням обмежень PostgreSQL max_connections.
Початковий запит:
     «Які порогові значення CPU та Memory обрати для HPA ASP.NET Core API, якщо запити до системи поділяються на легкі GET-ендпоінти (< 5 мс) і важкі Slicer- виклики (1–5 хв, CPU spike)?»
     Відповідь: Для систем із різнорідним навантаженням HPA за CPU є необхідним, але недостатнім: Slicer-виклики спричиняють короткі CPU-сплески, які HPA може не встигнути обробити через затримку масштабування (стандартно 30– 60 с). Рекомендований поріг CPU — 60–70%, щоб HPA реагував до перевантаження. Правильне рішення для CPU-інтенсивних операцій — винесення їх у фонову чергу (Hangfire, Channel), де вони виконуються у worker-pod-ах поза основним API. Memory 80% додає другий сигнал для масштабування при зростанні кількості одночасних Slicer-процесів.

     В.1.3 Запит 3: Організація спільного файлового сховища між pod-ами Kubernetes для STL та G-code файлів
Назва інструменту та версія: Claude Sonnet 4.6
     Мета використання: Визначення підходу до забезпечення доступу всіх реплік API до одних і тих самих STL та G-code файлів у локальному Kubernetes-кластері (minikube / Docker Desktop), з урахуванням обмежень доступних StorageClass.
     Внесок автора: Формулювання запиту на основі архітектурного рішення про збереження файлів у «/data» на pod-рівні, самостійний вибір ReadWriteMany PVC як рішення для локального кластера, розуміння обмежень та рекомендації щодо переходу на MinIO у продуктивному середовищі.
Початковий запит:
     «Як організувати спільний доступ кількох pod-ів ASP.NET Core до файлів STL та G-code у Kubernetes, якщо зараз файли записуються у локальну директорію «/ data» на pod-рівні?»
Відповідь:    Необхідний    PersistentVolumeClaim    із    accessMode
«ReadWriteMany» — він монтується одночасно у всі pod-и Deployment. У локальних кластерах (minikube, Docker Desktop) ReadWriteMany реалізується через hostPath або NFS provisioner. Для продуктивного середовища рекомендується об’єктне сховище (AWS S3, MinIO) із заміною запису у файлову систему на HTTP-виклики до S3-сумісного API — це повністю усуває залежність від спільного volume. Поточне рішення з PVC ReadWriteMany є прийнятним для навчального розгортання і демонструє концепцію спільного стану між репліками.
Уточнення:
     «Як передати шлях до спільного сховища у Kubernetes-розгортання без hard- code у коді застосунку?»

     Відповідь:  Шлях  передається  через  змінну  середовища, визначену  у  ConfigMap  або  безпосередньо  у  Deployment-маніфесті («env»   секція).   У   ASP.NET   Core   значення   зчитується   через
«IConfiguration» («builder.Configuration["FileStorage:BasePath"]»). ConfigMap дозволяє змінювати шлях без перезбірки образу — достатньо оновити ConfigMap і перезапустити pod-и через «kubectl rollout restart». Це відповідає принципу 12-factor app: конфігурація зберігається в середовищі, а не в коді.
