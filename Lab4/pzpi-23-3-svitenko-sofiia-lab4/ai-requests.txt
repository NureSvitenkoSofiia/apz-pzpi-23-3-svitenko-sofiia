== Запити до штучного інтелекту

=== Запит 1: Підготовка ASP.NET Core сервісу до stateless горизонтального масштабування

Назва інструменту та версія: Claude Sonnet 4.6

Мета використання: Визначення вимог до серверного застосунку на ASP.NET Core 10 для коректної роботи у горизонтально масштабованому середовищі Kubernetes з кількома ідентичними репліками за єдиним балансувальником навантаження.

Внесок автора: Формулювання запиту на основі аналізу архітектури PrintMaster, самостійна оцінка компонентів на наявність стану (JWT, Serilog, STL/G-code файли, DbSeeder), прийняття рішення про ReadWriteMany PVC та guard у DbSeeder, реалізація DbHealthCheck і Console sink.

Початковий запит:

«Які вимоги до ASP.NET Core застосунку для коректної роботи в режимі кількох ідентичних реплік за балансувальником навантаження? Які типові помилки призводять до некоректної роботи при горизонтальному масштабуванні?»

Відповідь: Основна вимога — відсутність стану між запитами (stateless). Типові проблеми: збереження стану у пам'яті (in-memory кеш, статичні колекції), серверні сесії, запис у локальну файлову систему без розподіленого сховища та виконання ініціалізаційних операцій (seeding) при кожному старті без перевірки. JWT-автентифікація є stateless за визначенням і не потребує змін. Файлове сховище слід виносити у спільний том (NFS, PVC ReadWriteMany) або об'єктне сховище. Seeder повинен містити guard-умову, яка перевіряє наявність даних перед вставкою.

Уточнення:

«Що потрібно додати до ASP.NET Core застосунку спеціально для Kubernetes, щоб кластер міг керувати lifecycle pod-а?»

Відповідь: Необхідно реалізувати ендпоінт readiness probe — Kubernetes не надсилатиме трафік на pod до отримання успішної відповіді. Для ASP.NET Core це робиться через `IHealthCheck` та `MapHealthChecks`. Liveness probe (той самий або окремий ендпоінт) дає Kubernetes сигнал перезапустити pod, якщо він перестав відповідати. Логи слід писати у stdout/stderr (`WriteTo.Console()`), оскільки файлові логи недоступні через `kubectl logs` без додаткових налаштувань.

=== Запит 2: Конфігурація HorizontalPodAutoscaler у Kubernetes для .NET застосунку

Назва інструменту та версія: Claude Sonnet 4.6

Мета використання: Визначення параметрів HPA для ASP.NET Core 10 API з урахуванням характеру навантаження PrintMaster (суміш легких GET-запитів і важких Slicer CPU-викликів) та обмежень локального кластера minikube / Docker Desktop.

Внесок автора: Формулювання запиту з урахуванням специфіки проєкту (Slicer-виклики як CPU spike, resource requests 250m CPU), самостійний вибір порогів CPU 70% і Memory 80%, встановлення maxReplicas 6 з урахуванням обмежень PostgreSQL max_connections.

Початковий запит:

«Які порогові значення CPU та Memory обрати для HPA ASP.NET Core API, якщо запити до системи поділяються на легкі GET-ендпоінти (< 5 мс) і важкі Slicer-виклики (1–5 хв, CPU spike)?»

Відповідь: Для систем із різнорідним навантаженням HPA за CPU є необхідним, але недостатнім: Slicer-виклики спричиняють короткі CPU-сплески, які HPA може не встигнути обробити через затримку масштабування (стандартно 30–60 с). Рекомендований поріг CPU — 60–70%, щоб HPA реагував до перевантаження. Правильне рішення для CPU-інтенсивних операцій — винесення їх у фонову чергу (Hangfire, Channel), де вони виконуються у worker-pod-ах поза основним API. Memory 80% додає другий сигнал для масштабування при зростанні кількості одночасних Slicer-процесів.

Уточнення:

«Скільки максимальних реплік встановити для HPA, якщо PostgreSQL обмежує загальну кількість з'єднань до 100?»

Відповідь: Кожна репліка ASP.NET Core підтримує пул з'єднань (за замовчуванням MaxPoolSize = 100 у Npgsql, але реально 10–20 активних під навантаженням). При 5–6 репліках загальна кількість з'єднань може перевищити 100. Безпечна межа — 4–6 реплік із зменшенням `MaxPoolSize` через рядок підключення або розгортанням PgBouncer у режимі transaction pooling між репліками і базою. Для навчальних цілей maxReplicas = 6 є прийнятним значенням із розумінням цього обмеження.

=== Запит 3: Організація спільного файлового сховища між pod-ами Kubernetes для STL та G-code файлів

Назва інструменту та версія: Claude Sonnet 4.6

Мета використання: Визначення підходу до забезпечення доступу всіх реплік API до одних і тих самих STL та G-code файлів у локальному Kubernetes-кластері (minikube / Docker Desktop), з урахуванням обмежень доступних StorageClass.

Внесок автора: Формулювання запиту на основі архітектурного рішення про збереження файлів у `/data` на pod-рівні, самостійний вибір ReadWriteMany PVC як рішення для локального кластера, розуміння обмежень та рекомендації щодо переходу на MinIO у продуктивному середовищі.

Початковий запит:

«Як організувати спільний доступ кількох pod-ів ASP.NET Core до файлів STL та G-code у Kubernetes, якщо зараз файли записуються у локальну директорію `/data` на pod-рівні?»

Відповідь: Необхідний PersistentVolumeClaim із accessMode `ReadWriteMany` — він монтується одночасно у всі pod-и Deployment. У локальних кластерах (minikube, Docker Desktop) ReadWriteMany реалізується через hostPath або NFS provisioner. Для продуктивного середовища рекомендується об'єктне сховище (AWS S3, MinIO) із заміною запису у файлову систему на HTTP-виклики до S3-сумісного API — це повністю усуває залежність від спільного volume. Поточне рішення з PVC ReadWriteMany є прийнятним для навчального розгортання і демонструє концепцію спільного стану між репліками.

Уточнення:

«Як передати шлях до спільного сховища у Kubernetes-розгортання без hard-code у коді застосунку?»

Відповідь: Шлях передається через змінну середовища, визначену у ConfigMap або безпосередньо у Deployment-маніфесті (`env` секція). У ASP.NET Core значення зчитується через `IConfiguration` (`builder.Configuration["FileStorage:BasePath"]`). ConfigMap дозволяє змінювати шлях без перезбірки образу — достатньо оновити ConfigMap і перезапустити pod-и через `kubectl rollout restart`. Це відповідає принципу 12-factor app: конфігурація зберігається в середовищі, а не в коді.
