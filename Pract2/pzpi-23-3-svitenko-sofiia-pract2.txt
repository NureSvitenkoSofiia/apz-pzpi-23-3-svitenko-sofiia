3 ОПИС ВИКОНАНОЇ РОБОТИ
3.1 Загальні відомості про систему
Mastodon — це вільне програмне забезпечення з відкритим вихідним кодом,
розробку якого розпочато у 2016 році в Німеччині. Система є децентралізованою
мікроблогінговою соціальною мережею — функціональним аналогом Twitter/X.
Серверна частина написана мовою Ruby з використанням фреймворку Ruby on
Rails, клієнтська — мовою TypeScript з використанням бібліотеки React.
Станом на 2024 рік мережа Mastodon налічує понад 13 000 активних
екземплярів і понад 8 мільйонів зареєстрованих облікових записів у всьому світі.
Стрімке зростання аудиторії відбулося наприкінці 2022 року після зміни власника
Twitter, що спричинило масову міграцію користувачів.
На відміну від єдиного централізованого сервісу, Mastodon являє собою
мережу незалежних екземплярів — серверів, кожен з яких управляється окремим
оператором, має власні правила та спільноту, водночас взаємодіючи з іншими
через стандартизований протокол ActivityPub. Проєкт розвивається некомерційною
організацією Mastodon gGmbH і фінансується переважно через Patreon.
3.2 Архітектурний стиль системи
Mastodon побудований на основі федеративної архітектури — архітектурного
стилю, при якому мережа складається з множини рівноправних автономних вузлів,
що взаємодіють за єдиним відкритим протоколом без центрального координатора.
Кожен екземпляр Mastodon є повноцінною самостійною системою з
власною базою даних, набором користувачів і контентом. Два екземпляри можуть
обмінюватися дописами, підписками та сповіщеннями — або ж адміністратор
одного екземпляра може заблокувати інший, і тоді обмін між ними припиняється.
З точки зору внутрішньої будови окремого екземпляра Mastodon реалізує
сервісно-орієнтовану архітектуру з кількома спеціалізованими процесами: вебсервер для обробки HTTP-запитів, окремий потоковий сервер для підтримки
з’єднань у реальному часі та система фонових черг для асинхронної обробки
завдань. Такий поділ дозволяє масштабувати кожен компонент незалежно.

3.3 Компонентна структура та стек технологій
Клієнтський застосунок (React + TypeScript) взаємодіє з сервером через два
незалежні канали: REST API для завантаження даних і WebSocket-з’єднання з
потоковим сервером для отримання оновлень у реальному часі.
Серверна частина на Ruby on Rails обробляє всі HTTP-запити, реалізує
бізнес-логіку, управляє автентифікацією та взаємодіє з базою даних. PostgreSQL
є основним сховищем усіх постійних даних: облікові записи, дописи, підписки,
медіавкладення. Redis виконує дві ролі: брокер повідомлень для системи черг
Sidekiq та кеш для тимчасових даних.
Sidekiq — система фонових черг на основі Redis — обробляє всі асинхронні
завдання: надсилання федеративних повідомлень, обробка медіафайлів, генерація
мініатюр. Потоковий сервер написаний окремо на Node.js і підтримує постійні
WebSocket-з’єднання з клієнтами. Elasticsearch є необов’язковим компонентом для
повнотекстового пошуку.
3.4 Протокол ActivityPub та механізм федерації
Федеративна взаємодія між екземплярами Mastodon ґрунтується на протоколі
ActivityPub — відкритому стандарті консорціуму W3C, прийнятому у 2018 році.
Кожен обліковий запис у Mastodon є актором (Actor) з унікальною адресою
у форматі URI — наприклад: «https://mastodon.social/@user». Кожен актор має
Inbox для прийому вхідних активностей та Outbox для публікації власних. Коли
користувач підписується на акаунт з іншого екземпляра, надсилається HTTP POST з
активністю типу «Follow». Після підтвердження екземпляр-хост починає надсилати
нові дописи на Inbox підписника.
Кожен запит підписується за допомогою HTTP Signatures з використанням
приватного RSA-ключа відправника. Отримувач перевіряє підпис за публічним
ключем з профілю актора. Дані передаються у форматі JSON-LD. Завдяки
ActivityPub користувачі Mastodon можуть підписуватися на акаунти з Lemmy,
PeerTube, Pixelfed та інших платформ Федіверсуму.

3.5 Організація стрічок новин та масштабування
Система підтримує три типи стрічок: домашня (дописи від підписаних
акаунтів), локальна (всі дописи екземпляра) та федеративна (всі дописи, відомі
екземпляру). Для формування домашньої стрічки Mastodon використовує підхід
«fan-out on write»: при публікації допису Sidekiq асинхронно додає його
ідентифікатор до Redis-списків усіх підписників. Для акаунтів з дуже великою
кількістю підписників застосовується протилежний підхід «fan-out on read» —
стрічка формується динамічно при запиті.
Черги Sidekiq розділені за пріоритетами: «default», «push» (федеративні
повідомлення), «pull» (отримання контенту), «mailers» (електронні листи).
Для великих екземплярів передбачено кілька паралельних процесів Puma за
балансувальником навантаження та окремий сервер PostgreSQL із репліками для
читання.

В.1 Запити до штучного інтелекту
В.1.1 Запит 1: Архітектурний стиль та протокол ActivityPub у Mastodon
Назва інструменту та версія: Claude Sonnet 4.6
Мета використання: З’ясування архітектурного стилю системи Mastodon,
принципів федеративної архітектури та механізму роботи протоколу ActivityPub для
підготовки теоретичної частини доповіді.
Внесок автора: Формулювання запиту на основі власного плану доповіді;
аналіз та фільтрація відповіді ШІ; самостійна адаптація до вимог академічного
стилю та структури звіту.
Початковий запит:
«Поясни архітектурний стиль системи Mastodon. Що таке федеративна
архітектура і як протокол ActivityPub забезпечує взаємодію між екземплярами? Чим
це відрізняється від централізованих соціальних мереж?»
Відповідь: Mastodon реалізує федеративну архітектуру — мережу автономних
вузлів без центрального координатора. Кожен екземпляр є самостійним сервером
із власною базою даних. ActivityPub — стандарт W3C (2018): кожен обліковий
запис є Actor з Inbox та Outbox; взаємодія відбувається через HTTP POST з JSONLD активностями, підписаними RSA-ключем (HTTP Signatures). Централізована
мережа (Twitter) має єдину точку відмови та єдиного оператора; федеративна —
розподіляє відповідальність між незалежними операторами.
Уточнення:
«Як саме відбувається підписка між двома різними екземплярами Mastodon?
Які HTTP-запити надсилаються і як перевіряється їхня автентичність?»
Відповідь: При підписці екземпляр A надсилає HTTP POST на «https://
instance-b.tld/inbox» з JSON-LD активністю типу «Follow», підписаною приватним
RSA-ключем акаунта-ініціатора. Ekземпляр B отримує запит, завантажує публічний
ключ актора з його профілю («/users/username»), перевіряє підпис HTTP Signatures
і, якщо перевірка пройшла, надсилає у відповідь активність «Accept». Після цього

18
екземпляр B додає Inbox екземпляра A до списку отримувачів нових дописів
підписаного акаунта.
В.1.2 Запит 2: Компонентна структура екземпляра Mastodon та роль Sidekiq
Назва інструменту та версія: Claude Sonnet 4.6
Мета використання: Отримання детального опису компонентної структури
екземпляра Mastodon — ролі кожного сервісу та принципу їх взаємодії — для
розділу звіту та відповідного слайда.
Внесок автора: Визначення рівня деталізації та переліку компонентів;
самостійна перевірка відповіді на відповідність офіційній документації Mastodon;
написання власного структурованого опису з акцентом на архітектурно значущі
рішення.
Початковий запит:
«Опиши компонентну структуру одного екземпляра Mastodon: які сервіси
запускаються, яку роль виконує кожен, чому Sidekiq розділений на окремі черги з
різними пріоритетами?»
Відповідь: Екземпляр запускає: Puma (Rails-вебсервер), Sidekiq (фонові
черги), Node.js Streaming API, PostgreSQL, Redis. Sidekiq використовує окремі
черги: «default» — більшість завдань; «push» — надсилання ActivityPubактивностей іншим екземплярам (критично для федерації); «pull» — отримання
контенту; «mailers» — листи. Розподіл пріоритетів гарантує, що навіть при
перевантаженні черги «default» федеративна доставка («push») не затримується.
Уточнення:
«Чому потоковий сервер Mastodon написаний окремо на Node.js, а не
вбудований у Rails?»
Відповідь: Rails (Puma) є багатопотоковим сервером із моделлю «один
потік на запит», оптимізованим для короткочасних HTTP-запитів. WebSocketз’єднання є довготривалими (хвилини, години) і блокують потік на весь час
з’єднання. Node.js з асинхронною моделлю event loop здатен підтримувати десятки

класичне архітектурне рішення: окремий сервіс для IO-bound задач.

В.1.3 Запит 3: Механізм fan-out on write та організація стрічок новин
Назва інструменту та версія: Claude Sonnet 4.6
Мета використання: Розуміння архітектурного рішення «fan-out on write»
для формування домашньої стрічки новин у Mastodon та його компромісів для
включення до відповідного розділу доповіді.
Внесок автора: Самостійне визначення теми запиту на основі вивчення
документації; оцінка відповіді ШІ; написання власного пояснення компромісу між
fan-out on write та fan-out on read з урахуванням контексту Mastodon.
Початковий запит:
«Поясни підхід fan-out on write у Mastodon для формування домашньої стрічки
новин. Які компроміси він передбачає і коли Mastodon перемикається на fan-out on
read?»
Відповідь: Fan-out on write: при публікації допису Sidekiq асинхронно записує
ідентифікатор допису до Redis-списку кожного підписника. При відкритті стрічки
клієнт зчитує список з Redis і завантажує дописи з PostgreSQL — операція читання є
O(1). Компроміс: операція запису масштабується як O(N) по кількості підписників;
для акаунта з 100 000 підписників — 100 000 записів до Redis при кожному дописі.
Fan-out on read застосовується для акаунтів із підписниками понад певний поріг:
стрічка будується SQL-запитом при кожному відкритті, що дорожче для читання,
але уникає O(N) записів.
