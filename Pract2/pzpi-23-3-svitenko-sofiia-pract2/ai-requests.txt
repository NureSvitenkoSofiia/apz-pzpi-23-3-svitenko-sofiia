== Запити до штучного інтелекту

=== Запит 1: Архітектурний стиль та протокол ActivityPub у Mastodon

Назва інструменту та версія: Claude Sonnet 4.6

Мета використання: З'ясування архітектурного стилю системи Mastodon, принципів федеративної архітектури та механізму роботи протоколу ActivityPub для підготовки теоретичної частини доповіді.

Внесок автора: Формулювання запиту на основі власного плану доповіді; аналіз та фільтрація відповіді ШІ; самостійна адаптація до вимог академічного стилю та структури звіту.

Початковий запит:

«Поясни архітектурний стиль системи Mastodon. Що таке федеративна архітектура і як протокол ActivityPub забезпечує взаємодію між екземплярами? Чим це відрізняється від централізованих соціальних мереж?»

Відповідь: Mastodon реалізує федеративну архітектуру — мережу автономних вузлів без центрального координатора. Кожен екземпляр є самостійним сервером із власною базою даних. ActivityPub — стандарт W3C (2018): кожен обліковий запис є Actor з Inbox та Outbox; взаємодія відбувається через HTTP POST з JSON-LD активностями, підписаними RSA-ключем (HTTP Signatures). Централізована мережа (Twitter) має єдину точку відмови та єдиного оператора; федеративна — розподіляє відповідальність між незалежними операторами.

Уточнення:

«Як саме відбувається підписка між двома різними екземплярами Mastodon? Які HTTP-запити надсилаються і як перевіряється їхня автентичність?»

Відповідь: При підписці екземпляр A надсилає HTTP POST на `https://instance-b.tld/inbox` з JSON-LD активністю типу `Follow`, підписаною приватним RSA-ключем акаунта-ініціатора. Ekземпляр B отримує запит, завантажує публічний ключ актора з його профілю (`/users/username`), перевіряє підпис HTTP Signatures і, якщо перевірка пройшла, надсилає у відповідь активність `Accept`. Після цього екземпляр B додає Inbox екземпляра A до списку отримувачів нових дописів підписаного акаунта.

=== Запит 2: Компонентна структура екземпляра Mastodon та роль Sidekiq

Назва інструменту та версія: Claude Sonnet 4.6

Мета використання: Отримання детального опису компонентної структури екземпляра Mastodon — ролі кожного сервісу та принципу їх взаємодії — для розділу звіту та відповідного слайда.

Внесок автора: Визначення рівня деталізації та переліку компонентів; самостійна перевірка відповіді на відповідність офіційній документації Mastodon; написання власного структурованого опису з акцентом на архітектурно значущі рішення.

Початковий запит:

«Опиши компонентну структуру одного екземпляра Mastodon: які сервіси запускаються, яку роль виконує кожен, чому Sidekiq розділений на окремі черги з різними пріоритетами?»

Відповідь: Екземпляр запускає: Puma (Rails-вебсервер), Sidekiq (фонові черги), Node.js Streaming API, PostgreSQL, Redis. Sidekiq використовує окремі черги: `default` — більшість завдань; `push` — надсилання ActivityPub-активностей іншим екземплярам (критично для федерації); `pull` — отримання контенту; `mailers` — листи. Розподіл пріоритетів гарантує, що навіть при перевантаженні черги `default` федеративна доставка (`push`) не затримується.

Уточнення:

«Чому потоковий сервер Mastodon написаний окремо на Node.js, а не вбудований у Rails?»

Відповідь: Rails (Puma) є багатопотоковим сервером із моделлю «один потік на запит», оптимізованим для короткочасних HTTP-запитів. WebSocket-з'єднання є довготривалими (хвилини, години) і блокують потік на весь час з'єднання. Node.js з асинхронною моделлю event loop здатен підтримувати десятки тисяч одночасних довготривалих з'єднань з мінімальними витратами пам'яті. Це класичне архітектурне рішення: окремий сервіс для IO-bound задач.

=== Запит 3: Механізм fan-out on write та організація стрічок новин

Назва інструменту та версія: Claude Sonnet 4.6

Мета використання: Розуміння архітектурного рішення «fan-out on write» для формування домашньої стрічки новин у Mastodon та його компромісів для включення до відповідного розділу доповіді.

Внесок автора: Самостійне визначення теми запиту на основі вивчення документації; оцінка відповіді ШІ; написання власного пояснення компромісу між fan-out on write та fan-out on read з урахуванням контексту Mastodon.

Початковий запит:

«Поясни підхід fan-out on write у Mastodon для формування домашньої стрічки новин. Які компроміси він передбачає і коли Mastodon перемикається на fan-out on read?»

Відповідь: Fan-out on write: при публікації допису Sidekiq асинхронно записує ідентифікатор допису до Redis-списку кожного підписника. При відкритті стрічки клієнт зчитує список з Redis і завантажує дописи з PostgreSQL — операція читання є O(1). Компроміс: операція запису масштабується як O(N) по кількості підписників; для акаунта з 100 000 підписників — 100 000 записів до Redis при кожному дописі. Fan-out on read застосовується для акаунтів із підписниками понад певний поріг: стрічка будується SQL-запитом при кожному відкритті, що дорожче для читання, але уникає O(N) записів.
