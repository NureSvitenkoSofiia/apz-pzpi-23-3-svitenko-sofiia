2 ЗАВДАННЯ

     Розробити мобільний програмний застосунок для поширеної мобільної платформи. Мобільний застосунок повинен бути частиною програмної системи PrintMaster — системи автоматизованого управління 3D-принтерами — та взаємодіяти з іншими її компонентами через REST API. Для реалізації застосунку використати технології нативної розробки для Android: мову Kotlin із застосуванням Jetpack Compose для побудови декларативного інтерфейсу, Navigation Compose для навігації між екранами, Ktor як HTTP-клієнт та Google Maps Compose для відображення карти принтерів. У звіті необхідно описати прийняті інженерні рішення, показати будову мобільного застосунку та його взаємодію з іншими частинами системи. Звіт має містити UML-діаграму прецедентів, UML-діаграму компонентів та не менше двох додаткових діаграм із визначеного переліку. У цій роботі додатково побудовано UML-діаграму діяльності для сценарію створення завдання друку та UML-діаграму станів для відображення життєвого циклу завдання. Код мобільного застосунку розміщується у складі репозиторію лабораторної роботи перед захистом.





3 ОПИС ВИКОНАНОЇ РОБОТИ
     У ході виконання лабораторної роботи було розроблено нативний мобільний застосунок для платформи Android у складі системи PrintMaster — програмної системи автоматизованого управління 3D-принтерами, призначеної для університетських лабораторій і makerspace-ів. Застосунок реалізовано мовою Kotlin із використанням Kotlin Multiplatform як каркасу проєкту, Jetpack Compose для побудови декларативного інтерфейсу, Navigation Compose для навігації між екранами, Ktor з плагіном Auth для HTTP-запитів і JWT Bearer-автентифікації, Gson для серіалізації, Google Maps Compose для карти принтерів та SharedPreferences для локального кешування даних і зберігання токена сесії.
     Мобільний застосунок є клієнтською частиною системи PrintMaster і не звертається безпосередньо до бази даних або IoT-контролера. Вся взаємодія з іншими компонентами відбувається через ASP.NET Core 10 REST API. Серверна частина зберігає завдання друку, матеріали і принтери, виконує конвертацію STL у G-code засобами PrusaSlicer та координує роботу IoT-контролера. Мобільний застосунок відповідає за надання користувачу зручного інтерфейсу для подачі завдань на друк та відстеження їхнього статусу.
     Кодова база Android-застосунку розміщена у теці «Mobile/androidApp/ src/main/kotlin/com/printing/app/». Пакетна структура застосунку відповідає чотирирівневій архітектурі і включає такі пакети: «data.remote» (API-клієнт і  окремі  API-інтерфейси),  «data.local»  (TokenStore  для  SharedPreferences),
«data.repository» (репозиторії), «domain.model» (доменні моделі), «ui» (екрани та ViewModel), «ui.navigation» (граф навігації) та «util» (LocaleHelper для перемикання мови).
     Архітектура мобільного застосунку побудована за шаровим принципом з чіткими межами відповідальності між шарами. UI-шар складається з декларативних Compose-екранів: «LoginScreen», «JobListScreen», «NewJobScreen» та «PrinterMapScreen», а також «SettingsSheet» — спливаючого меню налаштувань із перемикачем мови та виходом із системи. Екрани не виконують мережевих запитів безпосередньо, а відображають поточний стан, що надходить із відповідних ViewModel, та передають дії користувача назад до ViewModel. Навігацію між екранами описано у «AppNavGraph», який реалізує нижню панель навігації з трьома вкладками: «Завдання», «Нове» та «Карта».

Шар стану представлено класами «LoginViewModel», «JobViewModel» і
«MapViewModel». Кожна ViewModel зберігає реактивний стан відповідного екрана та виконує асинхронні операції у «viewModelScope». «JobViewModel» відповідає за завантаження списку завдань із кешуванням у SharedPreferences та відправку нового завдання на сервер. «MapViewModel» завантажує список принтерів і перемикає режим відображення між картою і списком. «LoginViewModel» обробляє введення облікових даних, виконує запит авторизації та зберігає отриманий JWT-токен у
«TokenStore».
Шар доступу до даних реалізовано через репозиторії «AuthRepository»,
«PrintJobRepository» і «PrinterRepository». Репозиторії приховують деталі HTTP-запитів від ViewModel і повертають уніфіковані результати. «PrintJobRepository» реалізує стратегію offline-first: спочатку повертає список завдань із кешу SharedPreferences, потім запитує сервер, оновлює кеш і повертає актуальні дані. Таке рішення дозволяє користувачу бачити останні відомі дані навіть без підключення до мережі.
     Мережевий шар побудовано на Ktor із плагіном ContentNegotiation (Gson) та Auth (Bearer). «ApiClient.kt» налаштовує HTTP-клієнт: плагін Auth завантажує токен  із  «TokenStore»  і  автоматично  додає  заголовок  «Authorization:  Bearer
<token>» до кожного запиту. Мережевий шар розділено на окремі API-інтерфейси:
«AuthApi»	(«POST	/api/auth/login»),	«PrintJobApi»	(«GET	/api/users/{id}/jobs»,
«GET /api/printjobs/materials», «GET /api/printer», «POST /api/printjobs» multipart) і
«PrinterApi» («GET /api/printer»).
     Локальне сховище застосунку обмежено мінімально необхідним набором даних. «TokenStore» у SharedPreferences зберігає JWT-токен, ідентифікатор і роль користувача для відновлення сесії після закриття застосунку. «PrintJobRepository» кешує список завдань у SharedPreferences у форматі JSON для офлайн-відображення. Це відповідає ролі мобільного клієнта у системі: він не дублює серверну базу даних, а зберігає лише стан, необхідний для автономної роботи інтерфейсу.
     Інтернаціоналізацію реалізовано через стандартний механізм ресурсів Android: файли «strings.xml» у директоріях «values/» (англійська) і «values-uk/»  (українська)  містять  усі  текстові  рядки  застосунку.  Перемикання

мови  виконується  через  «LocaleHelper»,  який  встановлює  нову  локаль у «attachBaseContext» і викликає «activity.recreate()» для перезавантаження інтерфейсу. Обрана мова зберігається у SharedPreferences «"settings"» → «"lang"» і відновлюється при наступному запуску.
     Основним користувацьким сценарієм є подача завдання на 3D-друк. Користувач входить у систему через «LoginScreen», потрапляє на «JobListScreen» зі списком своїх завдань, які відображаються з кольоровими чіпами статусу: Pending (жовтий), Printing (синій), Completed (зелений), Failed (червоний). У вкладці «Нове» відкривається «NewJobScreen», де користувач обирає матеріал із випадаючого списку (завантажується з «GET /api/printjobs/materials»), відповідний принтер (із «GET /api/printer»), а потім обирає STL-файл через
«ActivityResultContracts.GetContent». Після натискання «Відправити» формується multipart-запит «POST /api/printjobs» зі STL-файлом та параметрами. У вкладці
«Карта» «PrinterMapScreen» відображає маркери принтерів на Google Maps: зелений
— idle, синій — printing, сірий — offline. Натиск на маркер показує ім’я принтера та поточний статус. Кнопка перемикача дозволяє переключитися на список принтерів.
     Нижче наведено UML-діаграму прецедентів, яка показує функціональні можливості мобільного застосунку.




























Рисунок 3.1 – UML-діаграма прецедентів мобільного застосунку PrintMaster Діаграма прецедентів відображає двох акторів системи. Актор User ініціює
всі основні сценарії: вхід у систему, перегляд списку завдань, створення нового завдання (зі включенням підсценаріїв вибору STL-файлу, матеріалу та принтера), перегляд карти принтерів і зміну мови інтерфейсу. Актор System відповідає за автоматичну синхронізацію завдань і оновлення кешу. Зв’язок «<<include>>» використано для обов’язкових підсценаріїв при створенні завдання. Зв’язок
«<<extend>>» позначає опціональне переключення карти на режим списку.
     Наступна діаграма показує компонентну будову застосунку та його зв’язок із серверною частиною.




























Рисунок 3.2 – UML-діаграма компонентів мобільного застосунку PrintMaster Компонентна	діаграма	фіксує	межу	відповідальності	Android-клієнта.
Усередині пристрою розміщені: UI-шар із екранами та навігацією на Jetpack Compose, шар ViewModel, шар репозиторіїв та шар даних із Ktor-клієнтом і SharedPreferences-сховищами. За межами пристрою залишаються серверна частина на ASP.NET Core 10, база даних PostgreSQL та IoT-контролер ESP32. Мобільний застосунок спілкується з сервером виключно через HTTP/JSON із JWT Bearer-токеном.
     Для опису сценарію створення завдання побудовано UML-діаграму діяльності.



Рисунок 3.3 – UML-діаграма діяльності сценарію створення завдання друку

     Діаграма діяльності показує повний потік виконання операції від відкриття вкладки «Нове» до появи завдання у списку. Паралельно завантажуються матеріали через API та відображається індикатор завантаження. Після вибору матеріалу система фільтрує список принтерів до тих, що мають обраний матеріал. Якщо сервер повертає помилку, користувач бачить повідомлення і може повторити спробу. Успішне створення перенаправляє на список завдань, де нове завдання з’являється зі статусом Pending.
Окремо побудовано UML-діаграму станів для повного циклу завдання.



Рисунок 3.4 – UML-діаграма станів життєвого циклу завдання друку

     Діаграма станів відображає чотири основні стани завдання: Pending, Printing, Completed і Failed. Стан Pending включає внутрішні підстани: AwaitingSlice (очікування PrusaSlicer), Slicing (конвертація STL у G-code на сервері) і ReadyForPrint (G-code готовий). Стан Printing включає: Downloading (IoT завантажує G-code), Transmitting (передача команд принтеру через UART) і Monitoring (відстеження прогресу на LCD 20×4). Перехід Pending → Printing ініціює IoT-контролер через полінг черги кожні 10 секунд. Перехід до Completed або Failed виконується через «POST /api/printer/finish». Мобільний застосунок відображає фінальний стан кольоровим чіпом і повідомленням про помилку при Failed.
     Прийняті інженерні рішення узгоджені з роллю мобільного клієнта у системі. Ktor обрано замість Retrofit через нативну підтримку Kotlin Coroutines і зручний DSL для налаштування Bearer-автентифікації. Jetpack Compose спрощує підтримку кількох екранів із реактивним оновленням стану. SharedPreferences обрано для кешування завдань як достатній механізм для невеликих JSON-обсягів без накладних витрат Room. Navigation Compose дозволяє описати граф навігації декларативно та явно передавати параметри між екранами. Розподіл на окремі API-класи (AuthApi, PrintJobApi, PrinterApi) зменшує зв’язність і полегшує тестування кожного модуля незалежно.

ВИСНОВКИ

     В результаті виконання лабораторної роботи було розроблено нативний мобільний застосунок для Android-платформи у складі системи PrintMaster — програмної системи автоматизованого управління 3D-принтерами. Застосунок реалізує автентифікацію користувача з JWT Bearer-токеном, перегляд списку завдань друку з офлайн-кешем, подачу нового завдання з вибором STL-файлу, матеріалу та принтера, перегляд карти принтерів із Google Maps та перемикання мови інтерфейсу між українською та англійською.
     У роботі реалізовано чотирирівневу архітектуру: UI-шар на Jetpack Compose, шар ViewModel із StateFlow, шар репозиторіїв із offline-first стратегією та шар даних із Ktor-клієнтом і SharedPreferences. Мобільний застосунок не дублює серверну базу даних і взаємодіє з іншими компонентами системи виключно через REST API серверної частини на ASP.NET Core 10. Побудовані UML-діаграми показують функціональні можливості застосунку з точки зору акторів, компонентну будову та зв’язок із серверною частиною, потік виконання сценарію створення завдання та повний життєвий цикл завдання друку від подачі через мобільний клієнт до фізичного виконання IoT-контролером.

     Мета використання: Визначення підходів до реалізації стратегії offline-first у мобільному Android-застосунку без локальної реляційної бази даних для сценарію перегляду завдань 3D-друку.
     Внесок автора: Формулювання запиту з урахуванням конкретних обмежень проєкту (невеликий обсяг кешованих даних, відсутність потреби у складних запитах), самостійне прийняття рішення щодо SharedPreferences замість Room, реалізація патерну оновлення кешу після успішного мережевого запиту у PrintJobRepository.
Початковий запит:
     «Яку стратегію кешування обрати для мобільного Android-застосунку, який відображає список завдань із REST API, якщо потрібно показувати останні відомі дані при відсутності мережі, але обсяг даних малий і складні запити до локального сховища не потрібні?»
     Відповідь: Для невеликих обсягів JSON-даних без складних запитів SharedPreferences з Gson-серіалізацією є достатнім та легковагим рішенням. Патерн offline-first у цьому випадку реалізується в три кроки: при завантаженні екрана одразу повернути дані з кешу (якщо є), паралельно виконати мережевий запит, після успішної відповіді оновити кеш і повернути актуальні дані. Це дозволяє уникнути накладних витрат Room (анотації, DAO, міграції) там, де реляційна модель не потрібна.
Уточнення:
     «Як правильно обробити ситуацію, коли мережевий запит завершився помилкою і в кеші є застарілі дані — показувати дані з кешу чи повідомлення про помилку?»

     Відповідь: Якщо кеш не порожній — показати дані з кешу та необов’язково відобразити ненав’язливе повідомлення про відсутність оновлення. Якщо кеш порожній — показати помилку з кнопкою «Повторити». Такий підхід відповідає принципу «не переривати роботу користувача без потреби»: застарілі дані в більшості сценаріїв кращі за порожній екран, але потрібно чітко позначати їхню актуальність.
В.1.2 Запит 2: Bearer JWT-автентифікація у Ktor Client для Android

Назва інструменту та версія: Claude Sonnet 4.6
     Мета використання: Визначення підходу до налаштування автоматичного додавання JWT Bearer-токена до всіх HTTP-запитів у Ktor Client без ручного керування заголовком у кожному запиті.
     Внесок автора: Формулювання запиту на основі архітектурного рішення про Ktor замість Retrofit, самостійна реалізація ApiClient.kt із плагіном Auth і TokenStore, вибір підходу «sendWithoutRequest» для виключення ендпоінту «/api/ auth/login» з Bearer-автентифікації.
Початковий запит:
     «Як налаштувати Ktor Client для Android, щоб JWT Bearer-токен автоматично додавався до всіх запитів, крім ендпоінту логіну, якщо токен зберігається у SharedPreferences?»
     Відповідь: Ktor Auth plugin з конфігурацією bearer вирішує цю задачу через лямбду «loadTokens», яка зчитує токен зі сховища при кожному запиті. Параметр
«sendWithoutRequest» приймає лямбду-предикат, де можна перевірити URL запиту і повернути «false» для ендпоінту авторизації. Це позбавляє від необхідності вручну передавати або перевіряти токен у кожному API-методі — плагін централізовано обробляє автентифікацію.
Уточнення:
     «Чи потрібно налаштовувати «refreshTokens» у Ktor Auth, якщо серверний JWT живе 24 години і сесія не продовжується автоматично?»
     Відповідь: Якщо токен не поновлюється автоматично і 401 від сервера означає «вийти з системи», то «refreshTokens» не потрібен. Достатньо обробити 401-відповідь у шарі репозиторію або через «HttpResponseValidator», очистити

TokenStore і перенаправити на LoginScreen через StateFlow у ViewModel. Додаткова складність refreshTokens виправдана лише тоді, коли access token короткоживучий (5–15 хв) і є refresh token для беззупинної роботи.
В.1.3 Запит 3: Мультиpart завантаження STL-файлу через Ktor Client в Android

Назва інструменту та версія: Claude Sonnet 4.6
     Мета використання: Визначення правильного способу відправки STL-файлу разом із метаданими (materialId, printerId) у multipart/form-data запиті через Ktor Client з урахуванням отримання URI файлу через ActivityResultContracts.
     Внесок автора: Формулювання запиту на основі конкретного API-контракту сервера («POST /api/printjobs» з multipart), самостійна реалізація NewJobScreen із GetContent launcher та PrintJobApi з submitJob, адаптація відповіді до специфіки роботи з content URI в Android.
Початковий запит:
     «Як відправити STL-файл разом із додатковими полями (materialId, printerId) через Ktor Client у форматі multipart/form-data, якщо файл отримано як content URI через ActivityResultContracts.GetContent?»
Відповідь:	У	Ktor	Client	multipart-тіло	формується	через
«submitFormWithBinaryData». Для файлу, отриманого як URI, потрібно відкрити
«InputStream» через «contentResolver.openInputStream(uri)» і прочитати байти. У блоці «formData» файл додається як «PartData.FileItem» з MIME-типом «application/ octet-stream» і ім’ям файлу, додаткові поля — як «PartData.FormItem». Байти краще зчитувати у IO-диспетчері корутини, щоб не блокувати головний потік.
Уточнення:
     «Як правильно вказати ім’я файлу у multipart-запиті, якщо URI не завжди містить читабельне ім’я?»
     Відповідь: Ім’я файлу можна отримати через запит до «contentResolver» з колонками «OpenableColumns.DISPLAY_NAME». Якщо ім’я недоступне — використати «"model.stl"» як запасний варіант. Сервер ASP.NET Core отримає файл через «IFormFile» і матиме доступ до «FileName», тому правильне ім’я з клієнта полегшує логування та збереження файлу з читабельним ім’ям.
