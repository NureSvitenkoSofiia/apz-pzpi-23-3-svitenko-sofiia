2 ЗАВДАННЯ

     Розробити веб-застосунок як частину програмної системи PrintMaster — системи автоматизованого управління 3D-принтерами. Веб-застосунок повинен забезпечувати роботу двох категорій користувачів: звичайних користувачів, які подають завдання на 3D-друк, та адміністраторів, які виконують управління системою. Для реалізації використати сучасні технології front-end розробки: React Router 7 у режимі SPA, TypeScript, Tailwind CSS v4 та бібліотеку Recharts для візуалізації даних. Веб-застосунок повинен підтримувати інтернаціоналізацію (українська та англійська мови) та взаємодіяти з серверною частиною через REST API з JWT Bearer-автентифікацією. Адміністративна частина повинна забезпечувати: управління принтерами, матеріалами та користувачами (CRUD- операції), перегляд аналітичного дашборду з графіками, перегляд і очищення журналів сервера, а також експорт та імпорт даних у форматі JSON. У звіті необхідно описати прийняті інженерні рішення та показати будову застосунку і його взаємодію з серверною частиною. Звіт має містити UML-діаграму прецедентів, UML-діаграму компонентів та не менше двох додаткових діаграм.






3 ОПИС ВИКОНАНОЇ РОБОТИ
     У ході виконання лабораторної роботи було розроблено веб-застосунок PrintMaster Web — SPA-клієнт системи автоматизованого управління 3D- принтерами. Застосунок реалізовано на базі React Router 7 у режимі SPA з використанням TypeScript для статичної типізації, Tailwind CSS v4 для стилізації, i18next для інтернаціоналізації та Recharts для побудови аналітичних графіків. Взаємодія з сервером реалізована через axios із централізованим JWT Bearer- інтерцептором.
     Веб-застосунок є клієнтом серверної частини PrintMaster API на ASP.NET Core 10 і не містить власної бізнес-логіки обчислень. Він реалізує дві незалежні частини: інтерфейс для звичайних користувачів і адміністративний інтерфейс. Користувач переглядає список своїх завдань друку та подає нові через форму із drag- and-drop завантаженням STL-файлу. Адміністратор отримує доступ до аналітичного дашборду, CRUD-управління принтерами, матеріалами і користувачами, журналу подій сервера та сторінки резервного копіювання.
     Кодова база веб-застосунку розміщена у теці «Web/app/». Пакетна структура включає: «app/lib/» (сервісні модулі), «app/locales/» (файли перекладів),
«app/types/» (TypeScript-типи), «app/components/» (спільні компоненти), «app/ routes/» (сторінки та layout-компоненти) та файли «root.tsx» і «routes.ts» у корені
«app/».
     Архітектура застосунку побудована навколо React Router 7 file-based routing. Кожен файл у директорії «routes/» відповідає окремому маршруту або layout- компоненту. Два layout-компоненти реалізують рольовий захист: «_user.tsx» через
«clientLoader» перевіряє наявність JWT-токена та перенаправляє на сторінку входу, якщо токен відсутній; «_admin.tsx» перевіряє роль користувача та перенаправляє звичайних користувачів на їхній маршрут. Такий підхід дозволяє декларативно описати правила доступу в layout-компонентах без перевірок у кожній окремій сторінці.
Маршрутизацію описано у «routes.ts». Доступні маршрути: «/login» →
«login.tsx», «/» → «home.tsx» (редирект залежно від ролі), для ролі user через layout
«_user.tsx» — «/jobs» (список завдань) та «/jobs/new» (форма нового завдання), для ролі admin через layout «_admin.tsx» — «/admin/dashboard», «/admin/printers», «/ admin/materials», «/admin/users», «/admin/logs», «/admin/export».

     Мережевий шар централізовано реалізовано у «app/lib/api.ts». Модуль налаштовує axios-екземпляр із базовою URL та двома інтерцепторами. Request- інтерцептор зчитує JWT-токен із «localStorage» і додає заголовок «Authorization: Bearer <token>» до кожного запиту. Response-інтерцептор перехоплює відповіді зі статусом 401, очищає токен і роль із «localStorage» та перенаправляє користувача на сторінку входу. Цей модуль експортує функції для всіх API-ендпоінтів системи: автентифікація, завдання друку, матеріали, принтери, користувачі, аналітика, логи та системні операції.
     Інтернаціоналізацію реалізовано через «app/lib/i18n.ts» з пакетами i18next, react-i18next та i18next-browser-languagedetector. Файли перекладів «app/locales/ en.ts» та «app/locales/uk.ts» містять усі текстові рядки застосунку у вигляді TypeScript-об’єктів із типізованими ключами. Мова визначається автоматично через детектор (localStorage → navigator.language → fallback uk) і зберігається між сесіями. Компонент «LanguageSwitcher» доступний у «Navbar» (для користувача) та «AdminSidebar» (для адміністратора). Форматування дат виконується через
«Intl.DateTimeFormat» з поточною локаллю.
     Сторінка «_user.jobs.tsx» відображає список завдань друку поточного користувача (через «GET /api/users/{id}/jobs»). Кожне завдання відображається з компонентом «StatusChip», який обирає колір та текст відповідно до статусу: Pending (жовтий), Printing (синій), Completed (зелений), Failed (червоний). Дати форматуються через «Intl.DateTimeFormat» з урахуванням поточної мови інтерфейсу.
     Сторінка «_user.jobs.new.tsx» реалізує форму подачі нового завдання із drag- and-drop зоною для STL-файлу. Компонент обробляє події «dragover», «dragleave» і «drop» для візуального зворотного зв’язку. При виборі файлу відображається його ім’я у зоні завантаження. Форма також містить dropdown-список матеріалів (завантажується через «GET /api/printjobs/materials») та dropdown-список принтерів (через «GET /api/printer»). Після заповнення всіх полів кнопка «Відправити» стає активною. Запит «POST /api/printjobs» надсилається у форматі «multipart/form-data» із STL-файлом та ідентифікаторами матеріалу і принтера.
     Адміністративний дашборд «_admin.dashboard.tsx» отримує агреговані показники через кілька ендпоінтів і відображає їх у вигляді графіків Recharts:

«PieChart» для розподілу завдань за статусами, «BarChart» для відображення завантаженості принтерів та лічильники загальної кількості завдань, активних принтерів і рівня успішності.
     Сторінки «_admin.printers.tsx» та «_admin.materials.tsx» реалізують inline CRUD-таблиці: рядок таблиці перемикається в режим редагування при натисканні
«Редагувати»,  зміни  надсилаються  через  «PUT»-запит,  видалення  —  через
«DELETE». Для матеріалів додатково реалізовано вибір кольору через «<input type="color">», значення передається на сервер як HEX без символу «#». Сторінка
«_admin.users.tsx» відображає список користувачів із можливістю зміни ролі через SELECT-елемент, сторінка «_admin.logs.tsx» — журнал Serilog-логів із кнопкою очищення, сторінка «_admin.export.tsx» — завантаження поточного стану системи у JSON та завантаження файлу для імпорту.
Спільні  компоненти  («app/components/»)  розподілено  за  призначенням:
«Navbar» — верхня панель для розділу користувача, «AdminSidebar» — бічна панель адміністратора, обидва містять «LanguageSwitcher»; «StatusChip» — компонент відображення статусу завдання.
     Нижче наведено UML-діаграму прецедентів, яка описує функціональні можливості веб-застосунку для двох ролей.



Рисунок 3.1 – UML-діаграма прецедентів веб-застосунку PrintMaster

     Діаграма прецедентів виділяє двох акторів: User та Admin. Обидва актори можуть виконувати вхід і вихід із системи та перемикати мову інтерфейсу. User переглядає список своїх завдань та створює нові — останнє включає три обов’язкові підсценарії через зв’язок «<<include>>»: завантаження STL-файлу, вибір матеріалу та вибір принтера. Admin отримує доступ до дашборду, CRUD-управління принтерами, матеріалами і користувачами, журналу логів (із можливістю очищення через «<<extend>>»), а також до експорту та імпорту даних.
     Наступна діаграма показує компонентну будову веб-застосунку та його зв’язок із серверною частиною.















 Рисунок 3.2 – UML-діаграма компонентів веб-застосунку PrintMaster Компонентна діаграма відображає, що застосунок складається з кореневого
компонента «root.tsx», який ініціалізує i18n та підключає HTML-оболонку; шару маршрутизації («routes.ts», «_user.tsx», «_admin.tsx»); сторінок для двох ролей; спільних компонентів та бібліотечних модулів. Всі сторінки взаємодіють із сервером виключно через модуль «api.ts», який централізовано обробляє JWT- авторизацію та помилки.
Для опису сценарію подачі завдання побудовано UML-діаграму діяльності.



Рисунок 3.3 – UML-діаграма діяльності сценарію створення завдання друку

Діаграма діяльності показує потік виконання операції від відкриття сторінки
«/jobs/new» до появи нового завдання у списку. При відкритті форми паралельно завантажуються матеріали та принтери. Після вибору матеріалу dropdown принтерів показує лише ті, що мають обраний матеріал. Drag-and-drop зона приймає STL- файл і показує його ім’я. Лише після заповнення всіх полів кнопка «Відправити» стає активною. При помилці сервера форма залишається активною для повторної спроби, при успіху — відбувається перехід до «/jobs».
Для опису пакетної структури проєкту побудовано UML-діаграму пакетів.


Рисунок 3.4 – UML-діаграма пакетів веб-застосунку PrintMaster

     Пакетна діаграма показує поділ коду застосунку на окремі модулі. Пакет «lib/» містить сервісні модулі: «api.ts» з axios і JWT та «i18n.ts» з налаштуванням i18next. Пакет «locales/» зберігає типізовані файли перекладів. Пакет «types/» описує TypeScript-інтерфейси для всіх доменних сутностей. Пакет «components/» містить спільні UI-компоненти. Пакет «routes/» поділено на layout-компоненти та сторінки двох ролей. Центральні файли «root.tsx» та «routes.ts» координують ініціалізацію застосунку та визначення маршрутів.
     Прийняті інженерні рішення відповідають ролі веб-клієнта у системі. React Router 7 file-based routing обрано для декларативного опису маршрутів і природного розташування файлів. «clientLoader» у layout-компонентах дає можливість перевіряти автентифікацію на рівні маршрутизації до рендерингу сторінки. Централізований axios-модуль усуває потребу в перевірці токена в кожній

сторінці. i18next з browser-language-detector дозволяє зберігати мову між сесіями без додаткової логіки. Recharts обрано за нативну підтримку TypeScript і простоту інтеграції з React.

ВИСНОВКИ

     В результаті виконання лабораторної роботи було розроблено веб-застосунок PrintMaster Web як клієнтську частину системи автоматизованого управління 3D- принтерами. Застосунок реалізує повний інтерфейс для двох ролей: користувач переглядає список своїх завдань друку та створює нові через форму з drag- and-drop завантаженням STL-файлу; адміністратор керує принтерами, матеріалами і користувачами через CRUD-інтерфейси, переглядає аналітичний дашборд із графіками Recharts, журнал логів та виконує експорт і імпорт даних у форматі JSON. У роботі реалізовано рольовий захист маршрутів через «clientLoader» у layout-компонентах React Router 7, централізований axios-модуль із JWT Bearer- інтерцептором та автоматичним logout при 401, інтернаціоналізацію на базі i18next із підтримкою EN/UK та форматуванням дат через «Intl.DateTimeFormat». Побудовані	UML-діаграми	прецедентів,	компонентів,	діяльності	та	пакетів відображають функціональну модель застосунку, його компонентну будову та зв’язок із серверною частиною, потік виконання сценарію створення завдання та
пакетну структуру проєкту.

В.1.1 Запит 1: Рольовий захист маршрутів у React Router 7 через clientLoader

Назва інструменту та версія: Claude Sonnet 4.6
     Мета використання: Визначення підходу до реалізації рольового захисту маршрутів у React Router 7 без використання окремої бібліотеки авторизації для SPA з двома ролями (user та admin) і JWT-токеном у localStorage.
     Внесок автора: Формулювання запиту на основі архітектурного рішення про використання layout-компонентів як точок перевірки доступу, самостійна реалізація «_user.tsx» і «_admin.tsx» із «clientLoader», визначення логіки редиректу у «home.tsx» залежно від ролі.
Початковий запит:
     «Як реалізувати рольовий захист маршрутів у React Router 7, якщо JWT- токен і роль зберігаються у localStorage і потрібно перенаправляти незаконних користувачів до входу або до їхнього розділу до рендерингу сторінки?»
     Відповідь: React Router 7 підтримує «clientLoader» — функцію, яка виконується до рендерингу компонента маршруту. У layout-компоненті можна зчитати токен і роль із localStorage у «clientLoader» і повернути «redirect("/login")», якщо токен відсутній, або «redirect("/jobs")», якщо роль не відповідає вимогам. Такий підхід не потребує HOC або Context для захисту маршрутів — перевірка виконується декларативно на рівні маршрутизатора і не залежить від стану React- компонента.
Уточнення:
     «Як обробити випадок, коли токен є в localStorage, але вже застарів, і сервер повертає 401?»
     Відповідь: Оптимальне місце для обробки 401 — response-інтерцептор axios. При отриманні 401 інтерцептор очищає localStorage і виконує «window.location.href
= "/login"» (або «redirect» через React Router). Це дає єдину точку обробки прострочених	токенів	для	всіх	запитів,	не	потребуючи	логіки	у	кожному
«clientLoader» або компоненті.

     В.1.2 Запит 2: Drag-and-drop завантаження файлу на чистому React без зовнішніх бібліотек
Назва інструменту та версія: Claude Sonnet 4.6
     Мета використання: Визначення мінімального підходу до реалізації drag-and- drop зони для STL-файлу у React-компоненті без залежності від сторонніх бібліотек (react-dropzone та ін.) з правильною обробкою подій і візуальним зворотним зв’язком.
     Внесок автора: Формулювання запиту з урахуванням рішення уникати зайвих залежностей, самостійна реалізація drag-and-drop у «_user.jobs.new.tsx» із обробниками «dragover», «dragleave» і «drop», інтеграція з форматом «multipart/ form-data» для axios.
Початковий запит:
     «Як реалізувати drag-and-drop зону для вибору файлу у React-компоненті без зовнішніх бібліотек з коректним візуальним зворотним зв’язком при перетягуванні?»
Відповідь: Достатньо трьох обробників подій: «onDragOver» (викликати
«e.preventDefault()»	і	встановити	стан	«isDragging	=	true»),
«onDragLeave» («isDragging = false») і «onDrop» («e.preventDefault()», зчитати файл із «e.dataTransfer.files[0]», «isDragging = false»). Клас «isDragging» на контейнері змінює його стиль — підсвічування і пунктирна рамка — без зайвого коду. Скрита
«<input type="file">» дозволяє відкривати файловий менеджер при натисканні на зону, що забезпечує доступність.
Уточнення:
     «Як передати обраний через drag-and-drop файл у POST-запит axios у форматі multipart/form-data разом із іншими полями форми?»
     Відповідь: Для multipart-запиту через axios потрібно створити «FormData», додати  файл  через  «formData.append("stlFile",  file)»  і  текстові  поля  через
«formData.append("materialId", id)» тощо. Axios автоматично встановлює «Content- Type: multipart/form-data» із правильним boundary, якщо передати «FormData» як тіло запиту. Заголовок «Content-Type» не потрібно встановлювати вручну — ручне значення зламає boundary.

     В.1.3 Запит 3: Централізована обробка JWT у axios без дублювання логіки по компонентах
Назва інструменту та версія: Claude Sonnet 4.6
     Мета використання: Визначення підходу до організації HTTP-шару у веб-застосунку з JWT-автентифікацією так, щоб всі сторінки та компоненти використовували один axios-екземпляр без повторення логіки додавання заголовків і обробки помилок.
     Внесок автора: Формулювання запиту на основі архітектурного рішення про централізований «api.ts» замість розподілення axios-виклики по компонентах, самостійна реалізація request і response інтерцепторів, вибір localStorage як сховища токена для SPA без SSR.
Початковий запит:
     «Як організувати HTTP-шар у React SPA з JWT-автентифікацією, щоб токен автоматично додавався до запитів, а 401 оброблявся в одному місці, і компоненти не мали зайвої логіки авторизації?»
     Відповідь: Рішення — один axios-екземпляр із двома інтерцепторами, що живе в окремому модулі. Request-інтерцептор зчитує токен зі сховища і додає «Authorization: Bearer <token>» до «config.headers». Response-інтерцептор перехоплює помилки зі статусом 401 і виконує logout (очищення сховища і перенаправлення на сторінку входу). Всі сторінки використовують функції- обгортки цього модуля, а не сирий axios. Завдяки цьому компонент лише викликає
«getMyJobs()» і не знає, як саме передається токен.
Уточнення:
     «Чи варто зберігати JWT у localStorage або у httpOnly cookie для SPA без серверного рендерингу, якщо сервер є зовнішнім ASP.NET Core API?»
     Відповідь: Для SPA, де сервер — це зовнішній API (не той самий сервер, що роздає HTML), httpOnly cookie практично не реалізовати без CORS-налаштувань і «credentials: include» на клієнті та «SameSite: None; Secure» на сервері. У навчальному контексті localStorage є достатнім вибором. Для продуктивного застосунку рекомендується зберігати access token у пам’яті (змінна модуля), а refresh token — у httpOnly cookie, щоб захистити від XSS.
